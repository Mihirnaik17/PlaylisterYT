--------------------------------------------------------------------------------
SECURITY FIXES
--------------------------------------------------------------------------------

1. JWT tokens never expired
   File: server/auth/index.js, server/controllers/auth-controller.js
   BEFORE: jwt.sign() was called with no expiresIn, and the login cookie had no
           maxAge. A stolen cookie was valid FOREVER.
   AFTER:  Tokens expire after 7 days and the cookie carries a matching maxAge.

2. Server would run with a missing or placeholder JWT secret
   File: server/index.js
   BEFORE: If JWT_SECRET was unset (or left as "dev-secret" / "replace-me" from
           the docs/docker-compose defaults), the server started anyway —
           meaning anyone reading the repo could forge valid session tokens.
   AFTER:  Server refuses to start and prints a clear error until a real
           secret is configured.

3. No brute-force protection on login/register
   File: server/middleware/rate-limit.js, server/routes/auth-router.js
   BEFORE: Only the global limit (300 requests/min per IP) applied, allowing
           ~18,000 password guesses per hour per IP.
   AFTER:  Dedicated auth limiter: 20 attempts per 15 minutes on /auth/login
           and /auth/register (configurable via AUTH_RATE_LIMIT_* env vars).
           That's a ~99.5% reduction in feasible guess rate.

4. Private playlists leaked to any logged-in user
   File: server/controllers/store-controller.js (getPlaylists)
   BEFORE: GET /api/playlists returned EVERY playlist in the database,
           including other users' unpublished (private) ones.
   AFTER:  Returns published playlists only.

5. Mass-assignment on playlist creation
   File: server/controllers/store-controller.js (createPlaylist)
   BEFORE: The raw request body was spread into the new document, so a crafted
           request could set likes, listens, published, ownerUsername, etc.
   AFTER:  Only name and songs are accepted from the client; every other field
           is set server-side.

6. Regex injection in playlist search
   File: server/controllers/store-controller.js (searchPlaylists)
   BEFORE: (After the perf rewrite moved search into MongoDB $regex) raw user
           input in queries could produce invalid or pathological patterns.
   AFTER:  All search terms are regex-escaped before being used.

7. Missing security headers
   File: server/index.js
   BEFORE: No helmet — no X-Content-Type-Options, X-Frame-Options, HSTS, etc.
   AFTER:  helmet added (CSP disabled since this is a JSON-only API).

8. Oversized request body limit
   File: server/index.js
   BEFORE: express.json limit was 10mb — an easy memory-exhaustion vector.
   AFTER:  1mb, which is still ample for playlist payloads.

9. Comment input not validated
   File: server/controllers/store-controller.js (addComment)
   BEFORE: Any type/length accepted; a non-string or megabyte-long "comment"
           was stored as-is.
   AFTER:  Must be a non-empty string, trimmed, max 1000 characters.

10. /auth/edit relied only on an in-controller check
    File: server/routes/auth-router.js, server/controllers/auth-controller.js
    BEFORE: The route had no auth middleware; the controller did its own manual
            token check (one code path to get wrong).
    AFTER:  auth.verify middleware protects the route; the controller uses the
            middleware-verified req.userId.

--------------------------------------------------------------------------------
LOGIC / CORRECTNESS FIXES
--------------------------------------------------------------------------------

11. Lost-update race on listen counts
    File: server/controllers/store-controller.js (incrementListens)
    BEFORE: Read playlist -> increment in JS -> save. Two concurrent listeners
            could count as one.
    AFTER:  Atomic MongoDB $inc via findByIdAndUpdate.

12. updatePlaylist silently dropped lastAccessed (Mongo) and almost every
    field (Postgres)
    Files: server/db/mongodb/MongoDBManager.js,
           server/db/postgresql/PostgreSQLManager.js
    BEFORE: Mongo manager never applied lastAccessed even though controllers
            passed it. The Postgres manager only saved name/songs — publish,
            like, and comment updates were silently discarded on Postgres.
    AFTER:  Both managers apply the full supported field set (parity).

13. Song duplicate check used raw (possibly undefined) body values
    File: server/controllers/song-controller.js (updateSong)
    BEFORE: If you omitted a field when editing a song, the duplicate check
            compared against undefined and could miss real duplicates.
    AFTER:  The effective post-update identity (new value or existing value)
            is computed first and used for the check.

14. Implicit global function assignments
    Files: server/controllers/auth-controller.js
    BEFORE: getLoggedIn = async ... (no const) put controller functions on the
            global object — works only in sloppy mode and pollutes globals.
    AFTER:  Declared with const.

15. getLoggedIn error paths returned junk
    File: server/controllers/auth-controller.js
    BEFORE: On error it returned bare `false` as the JSON body with status 200,
            and a deleted user with a valid cookie caused a crash (null deref).
    AFTER:  Consistent { loggedIn, user } JSON; missing user handled.

16. YouTube oEmbed fetch ignored HTTP status codes
    File: server/controllers/youtube-controller.js
    BEFORE: A 404/500 response body was fed to JSON.parse, producing a
            confusing "Invalid JSON" error; timeout didn't destroy the socket.
    AFTER:  Non-200 statuses rejected explicitly; socket destroyed on timeout.

17. getAllSongs pagination was NaN-able and uncapped
    File: server/controllers/song-controller.js
    BEFORE: ?limit=abc produced NaN; ?limit=999999 dumped the whole collection.
    AFTER:  limit clamped to [1, 500], skip to >= 0, NaN-proof defaults.

18. Client auth state lost authReady flag
    File: client/src/auth/index.js (GET_LOGGED_IN reducer)
    BEFORE: The reducer omitted authReady, resetting it to undefined — the app
            gates rendering on this flag.
    AFTER:  authReady: true included.

19. Ctrl+Z hijacked while typing + leaked global key handler
    File: client/src/store/index.js
    BEFORE: document.onkeydown was reassigned on EVERY render with no cleanup,
            and Ctrl+Z triggered playlist-undo even while typing in a text
            field (fighting the browser's native text undo).
    AFTER:  Proper addEventListener in useEffect with cleanup; handler ignores
            events from INPUT/TEXTAREA/contentEditable and preventDefaults
            only when it actually handles the key.

--------------------------------------------------------------------------------
PERFORMANCE FIXES
--------------------------------------------------------------------------------

20. Playlist search loaded the ENTIRE collection into memory
    File: server/controllers/store-controller.js (searchPlaylists)
    BEFORE: Playlist.find({}) fetched every playlist, then filtered in JS.
            O(total playlists) memory and time per search request.
    AFTER:  Single indexed MongoDB query with all filters ($and of visibility
            + regex conditions), .lean(), capped at 200 results.
    METRIC: With N playlists, data transferred from DB drops from N documents
            to only matching documents (<= 200); the JS filtering pass is
            eliminated entirely.

21. getPlaylistsByUsername had the same full-collection scan
    File: server/controllers/store-controller.js
    BEFORE: Fetched all playlists, filtered in JS.
    AFTER:  Indexed find({ published: true, ownerUsername }) with .lean().

22. incrementListens did one DB round-trip per song (N+1)
    File: server/controllers/store-controller.js
    BEFORE: A 30-song playlist = 1 read + 1 write + 30 sequential updateOne
            calls = 32 round-trips per play.
    AFTER:  1 atomic findByIdAndUpdate + 1 bulkWrite = 2 round-trips total,
            regardless of playlist size. For a 30-song playlist that is a
            94% reduction in DB round-trips on the hottest endpoint.

23. Opening a playlist did a pointless write
    File: client/src/store/index.js (setCurrentList)
    BEFORE: GET playlist -> PUT the identical playlist back -> render. Doubled
            latency on every open and could clobber concurrent edits.
    AFTER:  GET only. One round-trip instead of two (~50% faster open).

24. Redundant double JWT verification on every protected request
    Files: server/controllers/store-controller.js, song-controller.js
    BEFORE: Routes ran auth.verify middleware AND each controller re-verified
            the same token via auth.verifyUser (duplicate crypto + parsing).
    AFTER:  Controllers trust the middleware-set req.userId. Also centralized
            the fetch-playlist + fetch-user + ownership-compare pattern into a
            single requireOwnership() helper (removes ~90 lines of copy-paste
            and a per-request getUserByEmail lookup in delete/update/publish).

24b. Infinite request loop on /api/playlistpairs after login (found post-pass)
    Files: client/src/components/MUIPlayPlaylistModal.js,
           client/src/store/index.js
    BEFORE: The play-playlist modal (mounted even when closed) had an effect
            that fetched playlist pairs whenever store.idNamePairs was empty,
            with store.idNamePairs as a dependency. For a user with zero
            playlists every response was a NEW empty-array reference, so the
            effect re-fired endlessly: continuous GET /api/playlistpairs
            requests that exhausted the rate limit and made every other API
            call fail with 429.
    AFTER:  The effect attempts the fetch at most once per mount (ref guard),
            and store.loadIdNamePairs() now shares a single in-flight request
            between concurrent callers as a second layer of defense.
    METRIC: playlistpairs requests after login: unbounded loop -> 1.

24c. Home page showed no playlists until "clear search filters" was clicked
    Files: client/src/components/MUIPlayPlaylistModal.js,
           client/src/components/CatalogSongCard.js, client/src/store/index.js
    BEFORE: store.idNamePairs held TWO different datasets — the Home page's
            published feed AND the logged-in user's own playlists (used by the
            play modal / song-card "Add to playlist" menus and My Music).
            The play modal (mounted even when closed) preloaded the user's
            pairs on login, and whichever response landed last overwrote the
            other — so the published feed vanished. Bonus bug: those "Add to
            playlist" menus could list the published feed (other people's
            playlists) instead of the user's own.
    AFTER:  The play modal and song cards fetch the user's own playlists into
            their own LOCAL state (only when opened) and never write to the
            shared field. addSongToPlaylist/likeCatalogSong no longer trigger
            a pairs reload that clobbered the feed.

24d. App crash (insertBefore/removeChild NotFoundError) when navigating away
     from a page with the YouTube player
    File: client/src/hooks/useYouTubePlayer.js
    BEFORE: new YT.Player(elementId) REPLACES the React-rendered div with an
            iframe. React's virtual DOM still referenced the replaced node, so
            the next route change crashed with "Failed to execute
            'insertBefore' on 'Node'" / "removeChild" NotFoundError.
    AFTER:  The hook imperatively creates a throwaway child div inside the
            React-rendered container and hands THAT to YT; destroy() clears
            the container. React-owned DOM is never touched by YouTube.

--------------------------------------------------------------------------------
NOTES FOR YOUR AWS DEPLOYMENT
--------------------------------------------------------------------------------

- Set a strong JWT_SECRET in the environment (the server now refuses to boot
  with placeholders like "dev-secret"). Generate one with:
      openssl rand -base64 48
- Point your ALB target-group health check at /health.
- server/.env contains real credentials (Mongo Atlas, OpenAI, Postgres). It is
  git-ignored, but rotate any of these if the repo was ever shared. On AWS,
  inject them via ECS task definition secrets / SSM Parameter Store instead of
  shipping a .env file.
- docker-compose.yml still defaults JWT_SECRET to "dev-secret" for local dev;
  the new boot check means production MUST override it (this is intentional).
- The rate limiters are per-instance (in-memory). If you scale to multiple
  containers behind an ALB, limits multiply by instance count; consider a
  Redis store for express-rate-limit if that matters.
- New optional env vars: AUTH_RATE_LIMIT_WINDOW_MS (default 900000) and
  AUTH_RATE_LIMIT_MAX (default 20).
